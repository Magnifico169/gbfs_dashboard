# Проверка M2

Запускать на отдельной пустой PostgreSQL 18: `seed.py` создаёт синтетическую систему `m2_benchmark`, 2500 станций и 365 дневных агрегатов одной станции. Это тестовые данные для нагрузки, не реальные наблюдения. Настроить PGHOST/PGPORT/PGUSER/PGPASSWORD/PGDATABASE на тестовую БД.

Из `services/api`:

```bash
uv run alembic upgrade head
uv run python ../../benchmarks/seed.py
ulimit -n 32768
DB_ROLE=app_api uv run uvicorn app.main:app --host 127.0.0.1 --port 58000 --no-access-log
```

В другом терминале, из корня репозитория:

```bash
ulimit -n 32768
uvx --from locust==2.47.0 locust -f benchmarks/locustfile.py --headless --users 1000 --spawn-rate 100 --run-time 45s --host http://127.0.0.1:58000 --csv benchmarks/results/1000 --only-summary
uvx --from locust==2.47.0 locust -f benchmarks/locustfile.py --headless --users 10000 --spawn-rate 1000 --run-time 45s --host http://127.0.0.1:58000 --csv benchmarks/results/10000 --only-summary
.venv/bin/python benchmarks/sse.py --users 1000 --duration 40
```

Параллельные обновления: из `services/api` выполнить `DB_ROLE=app_ingest uv run python ../../benchmarks/publish.py`. 30 пакетов по 2500 станций, пауза 5 секунд. Отдельный тест отказа `benchmarks/resilience.py` работает только с временным контейнером `gbfs-m2-test-pg`, опубликованным на 55439, и API на 58000: временно запрещает TCP-доступ к этой БД, завершает её TCP-сессии и обязательно восстанавливает правила подключения. Не запускать его на рабочем окружении.

## Замер 16 ноября 2026

WSL Ubuntu, 32 видимых CPU, 5923 MiB памяти, PostgreSQL 18, один процесс Uvicorn, Python 3.12, Locust 2.47.0. API и генератор работают на одной машине. Пользователь делает запрос с паузой 5–30 секунд; смесь: список станций, карточка и год дневных агрегатов. Короткие прогоны по 45 секунд включают разгон; это локальный замер, а не подтверждение длительной производственной ёмкости.

- 1000 пользователей: 2854 запроса, 0 ошибок, 64.7 RPS, p95 360 мс, p99 470 мс. Годовой агрегат: p95 290 мс, p99 320 мс.
- 10000 пользователей, один процесс: 27556 запросов, 609.1 RPS, p95 2800 мс, p99 3100 мс. 3935 запросов отклонены явным HTTP 503 при стартовой перегрузке; таймаутов сокетов нет. Для этой нагрузки нужны дополнительные процессы/реплики.
- 1000 SSE-клиентов: все получили полный снимок 2500 станций и оставались подключены до конца 40-секундного теста; p95 начального подключения и передачи снимка — 16.7 с. Одновременная передача больших начальных снимков остаётся дорогой; это не задержка одиночной дельты.
- Первая запись 2500 состояний — 0.185 с. Полный R-пересчёт тестового набора 2500 станций — 100.343 с, меньше интервала воркера 600 с.
- При потере БД: чтение 503, readiness 503, liveness 200; после восстановления чтение 200. При остановке приёма последнее состояние сохраняется и помечается устаревшим по времени источника/опроса.

Первый стресс-прогон выявил лимит окружения 1024 дескриптора; итоговые результаты на 10000 сняты с `nofile=32768`. Были также устранены повторная сериализация отчётов и неограниченное ожидание HTTP-запросов.

Машиночитаемые метрики: [results/summary.json](results/summary.json). Сырые CSV и логи повторных прогонов создаются локально; в результат включена сводка, промежуточные файлы удалены. Автоматические проверки Python/R и миграций выполняются в `.github/workflows/tests.yml`.
