# 0001. Берём живой GBFS-фид как источник вместо учебного дампа

## Контекст и постановка задачи

Нужен дашборд с разделением по ролям «оператор — менеджер». Предложенный вариант — готовый дамп базы магазина видеопроката: там уже есть филиалы, инвентарь и аренды, и роли на них ложатся.

Но дамп статичен. Ни реального времени, ни накопления истории, ни приёма данных в нём нет — задача сводится к написанию `SELECT`. Вопрос: где взять предметную область с теми же ролями, но с настоящей динамикой.

## Факторы решения

* Нужен источник, состояние которого меняется быстрее, чем раз в сутки
* Нужна предметная область, где «оператор следит за филиалами» и «менеджер считает продукцию» не выглядят натянуто
* Доступ без ключей и без согласований: проект учебный
* Источник не должен исчезнуть в середине работы

## Рассмотренные варианты

* Дамп базы магазина видеопроката
* GBFS — открытый стандарт фидов велопроката и кикшеринга
* Wikimedia EventStreams — поток правок Википедии
* NYC 311 — обращения граждан через SODA API
* Московская биржа, ISS API

## Принятое решение

Выбран **GBFS**, потому что это единственный из рассмотренных источников, где предметная область изоморфна исходной задаче: станция — это филиал, велосипед — единица инвентаря, поездка — аренда, и при этом состояние меняется каждые 10–60 секунд.

Эталонная система — Citi Bike (`lyft_nyc`), фид `https://gbfs.citibikenyc.com/gbfs/en/gbfs.json`.

> В контексте учебного дашборда с ролевым разделением, сталкиваясь с тем, что готовый дамп не даёт ни динамики, ни приёма данных, мы выбрали живой GBFS-фид, чтобы получить настоящую предметную область с реальным временем, соглашаясь на то, что историю придётся накапливать самим и первые недели дашборд будет полупустым.

### Последствия

* Хорошо: появляется содержательный слой приёма данных, который в варианте с дампом отсутствует полностью
* Хорошо: смена системы не требует изменений в схеме — в реестре 1539 систем, у 1532 из них нет авторизации
* Плохо: истории в фиде нет вообще, накопление начинается с нуля
* Плохо: данные чужие и грязные, нужен отдельный слой очистки (см. ADR-0003)

### Проверка

Поллер пишет строки в `core.station_status`, и `app.ingest_run` показывает успешные запуски за последние сутки.

## Плюсы и минусы вариантов

### Дамп магазина видеопроката

* Хорошо: данные согласованы, роли очевидны, работает сразу
* Плохо: статика; реального времени нет, приём данных проектировать не из чего

### GBFS

* Хорошо: 1539 систем, 1532 без авторизации; станции, вместимость, состояние каждые 10–60 с
* Хорошо: домен совпадает с исходной задачей один в один
* Плохо: событий аренды нет, только состояние (см. ADR-0003)

### Wikimedia EventStreams

* Хорошо: настоящий поток SSE без ключей и лимитов, десятки событий в секунду
* Плохо: домен не про инвентарь и филиалы, объяснять пришлось бы дольше

### NYC 311

* Хорошо: 40+ млн записей с 2010 года, готовая история, 300+ типов обращений
* Плохо: обновление батчами с задержкой в часы — «реального времени» нет

### MOEX ISS

* Хорошо: открытый API без ключа, богатая история свечей
* Плохо: роли «трейдер и риск-менеджер» далеки от исходной постановки; вне торговых часов данные не меняются
