# 0002. Архитектура, роли и pipeline данных (итерация M0)

## Контекст

Дашборд GBFS для трёх ролей (оператор, менеджер, администратор), источник — открытые фиды (ADR-0001). Требования итерации: обработка данных на R, остальное на Python; графики считает клиент; docker сейчас, Helm позже; охват — почти весь реестр GBFS; система должна оставаться устойчивой при 1000+ одновременных пользователей (≈ 30–200 RPS на чтение при обновлении раз в 5–30 с).

Ограничения источника: нет истории, нет событий аренды (только счётчики), v2.x и v3.0 называют поля по-разному, данные грязные.

## Решения

### 1. Языки

* **R** — сервисы обработки данных: опрос фидов, нормализация v2/v3, валидация, вывод событий из дельт, ролл-апы, аналитика.
* **Python (FastAPI)** — всё, что обслуживает пользователей: API, аутентификация, роли, задачи, админка, SSE.

Опрос фидов — I/O-bound (~100 запросов/с на весь реестр), язык скорости получения данных не меняет; опрос на R ради единого пути «получили → нормализовали → записали». R однопоточен: масштабируем числом процессов (шардирование систем). Пользовательский трафик R не обслуживает.

### 2. Хранилище: только PostgreSQL 18

ClickHouse не берём: он оправдан при сыром хранении сотен млн строк в сутки, но добавляет вторую БД (эксплуатация, репликация, нет транзакций), а отчёты читают ролл-апы. Реализация:

* факты — таблицы с декларативным партиционированием по времени, старые партиции удаляются целиком (сырые — 30–90 дней);
* запись батчами через `COPY`, строка не пишется, если состояние станции не изменилось;
* ролл-апы 10 мин / час / день хранят суммы, счётчики, min/max (не средние); границы суток и месяцев — по таймзоне системы;
* текущее состояние — таблица `core.station_current`, одна строка на станцию.

Доступ к фактам — через тонкий слой, чтобы вынос в ClickHouse не затронул остальное. **Критерий пересмотра** (замер на M2): запись не успевает за приёмом; отчёт за год на дневном уровне дольше целевого; размер сырых данных неприемлем.

### 3. Владение данными: кто пишет, кто читает

Правило: **у каждой таблицы ровно один писатель**. Различие закрепляется ролями БД (`app_ingest` пишет в `core`/`mart`, `app_api` пишет только в `app`, остальное читает), а не договорённостью.

| Данные | Пишет | Читает | Операция |
|---|---|---|---|
| `core.system`, `region`, `station` (SCD2), `vehicle_type` | **R** | Python | справочники, раз в час/сутки из `station_information`, `system_information`, `vehicle_types` |
| `core.station_current` | **R** | Python (оператор) | upsert на каждый приём `station_status`; экран «сейчас» |
| `core.station_status` (факты) | **R** | Python (админ, карточка станции) | `COPY` только изменившихся строк |
| `core.station_event` | **R** | Python | события из дельт; лента на карточке станции, источник автозадач |
| `core.station_quarantine` | **R** | Python (админ) | снимки, не прошедшие валидацию, с причиной |
| `mart.*` (10 мин / час / день) | **R** | Python (менеджер) | пересчёт по расписанию, идемпотентный |
| `app.ingest_run` | **R** | Python (админ) | журнал запусков по фидам: статус, строк, HTTP-код, ошибка |
| `app.user_account`, `role`, `user_scope` | **Python** | Python | пользователи, роли, зоны |
| `app.rebalance_task` | **Python** | Python, R (аналитика план/факт — только чтение) | создание, взятие, закрытие с фактическим количеством |
| `app.audit_log` | **Python** | Python | действия пользователей |
| `app.report_schedule`, настройки систем | **Python** | R (читает список активных систем и интервалы опроса) | управление из админки |

Автозадачи (по `stockout_begin`): R только пишет событие; задачу создаёт Python, читая новые события. Так задачи остаются у одного писателя.

### 4. Взаимодействие сервисов: через БД, без брокера

Прямых вызовов между R и Python нет. Сигнал «пришёл новый снимок» — `NOTIFY`; API по нему сбрасывает кэш и шлёт клиентам дельту по SSE. Потерянный сигнал не критичен: кэш истекает по TTL, система деградирует до поллинга. Kafka не берём: один источник записи, один набор читателей, воспроизведение потока не требуется. Пересмотр — при нескольких независимых потребителях потока или превышении возможностей БД (тогда NATS JetStream / Kafka).

### 5. Pipeline данных

```
GBFS-фид
  → [R] опрос по ttl/ETag, таймаут, retry с backoff; запись в app.ingest_run
  → [R] разбор, нормализация v2/v3 → единая модель
  → [R] валидация: неотрицательные счётчики; доступные + неисправные ≤ capacity;
        last_reported не из будущего.  Не прошло → core.station_quarantine
  → [R] сравнение с core.station_current: изменилось?
        да  → COPY в core.station_status, upsert в station_current,
              вывод событий в core.station_event
        нет → обновляем только метку проверки
  → [R] NOTIFY 'snapshot_ready'
  → [R, по расписанию 10 мин] ролл-апы → mart.*
  → [Python] читает, накладывает роль и зону, кладёт в кэш 2–5 с по (система, зона, вид)
  → [Python] отдаёт JSON + SSE-дельты
  → [Браузер] рисует таблицы, карту и графики сам
```

Метод вывода событий даёт нижнюю оценку оборота (взяли и вернули между опросами — события нет); интерфейс менеджера обязан это показывать. «Пусто» (0 доступно, станция жива) отличаем от «неизвестно» (давно нет `last_reported`).

### 6. Фронтенд

Данные отрисовывает **браузер**: сервер отдаёт компактные агрегаты, графики строит клиентская библиотека (uPlot / ECharts), карту — MapLibre/Leaflet. Интерфейс отдаёт Python: серверные шаблоны Jinja, обновления через HTMX и SSE, JS — только для графиков и карты. SPA не берём: один язык на сервере, меньше сборки и кода. R рисует графики только для PDF/PNG-отчётов по расписанию.

### 7. Функции ролей

**Оператор** (горизонт: сейчас и последний час, только своя зона):
* смена: плитки (станций в зоне, доступность, требуют выезда, открытых задач), список проблемных станций по критичности, карта зоны, лента событий;
* **справка для внешних обращений**: поиск станции по названию/адресу/точке на карте → сколько доступно (обычных/электрических), свободных мест, неисправных, возраст данных, объявленные работы; ближайшие станции с доступным транспортом;
* карточка станции: график за сутки, события, создание задачи (предзаполнено из состояния);
* задачи: очередь, «взять», закрытие с фактическим количеством; автозадачи помечены отдельно.

**Менеджер** (горизонт: сутки, месяц, год, произвольный интервал; только агрегаты, сырых снимков нет):
* обзор сети: плитки, спрос по часам суток, часы простоя в нуле/переполнения по зонам;
* рейтинг станций (сортируемый; по умолчанию «на место», а не по абсолютному обороту);
* парк: состав по зонам, доля электрических и её тренд, качество данных источника;
* выбор периода (год / месяц / интервал) и сравнение с предыдущим; в ответе указан уровень гранулярности и точность;
* участие в распределении: рекомендации по перебросу (откуда → куда, сколько), утверждение и назначение задач; план/факт по выполнению;
* экспорт CSV и PDF.

**Администратор**:
* приём данных: запуски по фидам, доля неуспешных, задержка последнего успешного, ошибки, карантин и причины;
* системы: реестр, включение/выключение, интервалы опроса;
* хранилище: партиции, лаг ролл-апов, размеры;
* пользователи, роли, зоны; журнал действий.

### 8. Права как свойство данных

Оператор видит только свою зону; фильтр зоны навязывается сервером и RLS в PostgreSQL. Забытый контекст зоны даёт пустой ответ с объяснением (fail closed), не чужие данные. У менеджера нет прав на `core.station_status` и `station_current` на уровне БД. Права зашиты в токен и проверяются локально, без обращения в БД на каждый запрос.

### 9. Обработка ошибок на стороне оператора

Экран не показывает устаревшее как актуальное и не молчит о причине пустоты. У каждой цифры есть «по состоянию на», у каждой ошибки — код, понятный текст и `request_id`.

| Ситуация | Что видит оператор | Поведение |
|---|---|---|
| Приём остановлен | Баннер «данные устарели на N мин» | Последние значения с возрастом |
| Станция давно не отчитывалась | «Потеряна связь», не «0» | «пусто» ≠ «неизвестно» |
| Зона не задана / нет прав | «Зона не выбрана» + выбор | Fail closed |
| Проблем нет | «Вмешательство не требуется» | Отличается от пустой выборки |
| Обрыв SSE | «Нет связи, данные на HH:MM:SS» | Переподключение с backoff и jitter, откат на поллинг |
| Невалидные данные | «Данные недостоверны» | Карантин, вне агрегатов |
| Ошибка действия | Сообщение, ввод сохранён | Идемпотентные запросы |
| Конфликт (задачу взял другой) | «Уже в работе у …» | Оптимистичная блокировка |

### 10. Отказоустойчивость при 1000+ пользователей

* раздаёт только Python, без состояния, масштабируется горизонтально; пробы `/livez`, `/readyz`;
* кэш ответов 2–5 с на процесс — запросы одной зоны не умножают нагрузку на БД;
* push по SSE вместо поллинга; лимиты запросов на пользователя; таймауты на каждый внешний вызов; ограниченные очереди; при перегрузке `429/503` с `Retry-After`;
* изоляция: сбой приёма не ломает чтение (показываем последнее с возрастом), тяжёлые отчёты менеджера идут отдельным пулом соединений и не влияют на оператора.

Проверка — нагрузочный тест (k6/locust) на M2: 1000 одновременных клиентов, затем 10×; p95/p99, доля ошибок, поведение при остановке R-приёма и при потере БД.

### 11. Развёртывание

Сейчас — docker compose. Далее Helm-чарт: API без состояния и R-воркеры (шардированные по системам) как отдельные Deployment, PostgreSQL — внешний или оператор. Решение откладывается до M7.

## Открытые вопросы

Решено: **фронтенд** — Jinja + HTMX + SSE; **аутентификация** — собственные логины в `app.user_account` (SSO не нужен); **зоны оператора** — задаёт администратор вручную, по умолчанию одна зона «вся система» (поверх `region_id`, где он есть).

Открыто:

1. **Автозадачи и рекомендации по перебросу:** какие правила (порог пустоты, время простоя) и считает ли их R-аналитика или SQL?
2. **Внешние обращения пользователей:** это просто справка для оператора (раздел 7) или требуется журнал обращений (кто звонил, что спросил)?
3. **Выбор системы:** оператор/менеджер работают в одной системе за сеанс или переключаются между ними?

## Последствия

* Хорошо: одна БД, чёткое владение таблицами, простое развёртывание, нет брокера
* Хорошо: графики на клиенте не масштабируются с числом пользователей на сервере
* Плохо: сырые данные хранятся 30–90 дней, глубже — только ролл-апы
* Плохо: R масштабируется процессами; полный реестр потребует шардирования
* Плохо: вынос фактов в ClickHouse, если понадобится, — отдельная работа
