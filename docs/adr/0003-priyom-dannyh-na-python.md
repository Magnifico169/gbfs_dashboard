# 0003. Приём данных на Python, R — только аналитика

## Контекст и постановка задачи

ADR-0002 отдавал R весь путь данных: опрос фидов, нормализацию v2/v3, валидацию и запись, а Python — всё, что обслуживает пользователей. В M1 это было реализовано на R, и вскрылись проблемы:

* требование проекта — R только для обработки данных (ролл-апы, профили, прогноз), а получение и разбор API в него не входят;
* схему БД и миграции ведёт Alembic (Python), а код приёма на R работал с таблицами голым SQL: описание схемы дублировалось, ORM в R нет;
* аргумент «единый путь» не опирался на скорость: опрос фидов — I/O-bound, язык на него не влияет (отмечено уже в ADR-0002).

## Факторы решения

* Одно описание схемы для миграций, приёма и будущего API
* Скорость приёма определяется сетью и БД, а не языком
* R нужен там, где у него преимущество: статистика и прогнозирование
* Правило «у каждой таблицы один писатель» должно сохраниться

## Рассмотренные варианты

* Оставить приём на R, миграции на Alembic
* Приём на Python (ORM SQLAlchemy), R — только аналитика

## Принятое решение

Выбран **приём на Python**: воркер приёма в приложении `services/api` (общие настройки, модели и слои с FastAPI-API) опрашивает фиды, нормализует v1.1/v2/v3 pydantic-схемами, валидирует и пишет `core.*` и `app.ingest_run` через ORM SQLAlchemy; ORM-модели — единственный источник схемы, по ним Alembic генерирует ревизии. R переезжает в `services/analytics` (M2): читает `core`, пишет `mart.*`.

> В контексте проекта, где R предназначен для обработки данных, а схему ведёт Alembic, сталкиваясь с дублированием схемы и размытой границей ролей языков, мы перенесли приём данных на Python, чтобы иметь одно описание таблиц и чёткое разделение «получение и запись — Python, аналитика — R», соглашаясь на то, что код приёма, написанный на R в начале M1, переписан.

### Что меняется в ADR-0002

* п. 1: опрос, нормализация и валидация — Python; R — ролл-апы, профили загрузки, прогноз, отчёты PDF/PNG;
* п. 3: писатель `core.*` и `app.ingest_run` — сервис приёма на Python; писатель `mart.*` — R; правило «один писатель на таблицу» сохраняется, роль БД `app_ingest` — у приёма, отдельная роль для R добавится в M2;
* п. 5: шаги до `core.station_status` и `station_current` выполняются на Python; ролл-апы — на R;
* п. 11: контейнеры `migrate`, `ingest` (воркер того же приложения), `api`, позже `analytics` (R); у каждого своя роль БД (`app_ingest`, `app_api`).

### Последствия

* Хорошо: схема описана один раз, миграции проверяются `alembic check`
* Хорошо: тесты приёма поднимают схему настоящим Alembic
* Хорошо: R без сетевого кода, проще образ и тесты аналитики
* Плохо: нормализация и валидация переписаны, фикстуры и поведение сохранены тестами
* Плохо: запись батчами идёт через ORM-вставки, а не `COPY` (при ~2500 строк на опрос различия не измерялись; пересмотр — по замерам на M2)

### Проверка

Один проход по живому фиду Citi Bike пишет в `core.station_status` изменившиеся станции, повторный проход — 0 строк; `uv run pytest` и `alembic check` проходят.
