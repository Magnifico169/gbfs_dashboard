# M3: аутентификация, роли и зоны

M3 добавляет обязательную авторизацию к API M2. Публичны пробы /livez, /readyz и описание OpenAPI; данные, SSE и административные операции требуют заголовок Authorization: Bearer <access_token>.

## Запуск

1. Задайте в .env отдельный AUTH_SECRET для всех реплик API. Сгенерировать значение: python3 -c 'import secrets; print(secrets.token_urlsafe(48))'. Минимум 32 байта; встроенного секрета нет. Без него вход и проверка токенов возвращают 503 auth_not_configured.
2. Выполните docker compose up -d --build --wait. Сервис migrate применит ревизию 0003 поверх M2.
3. Создайте первого администратора: docker compose exec api python -m app.bootstrap admin. Пароль вводится скрыто дважды, минимум 12 символов. Команда отказывается работать, если администратор уже существует. Следующих пользователей создаёт администратор через API.
4. Откройте /docs, выполните POST /api/v1/auth/login и вставьте полученный access_token в **Authorize**. Администратору system_id можно не передавать.

При локальном запуске:

~~~bash
uv sync
cd services/api
uv run alembic upgrade head
uv run python -m app.bootstrap admin
DB_ROLE=app_api uv run uvicorn app.main:app --reload
~~~

## Вход и сеанс

POST /api/v1/auth/login принимает JSON:

~~~json
{"username": "operator", "password": "<пароль>", "system_id": "lyft_nyc"}
~~~

Ответ: access_token, refresh_token, token_type: "bearer", expires_in.

- Пароли хранятся как Argon2id-хеши. Неизвестный пользователь и неверный пароль дают одинаковый 401 invalid_credentials; отключённая учётная запись также не может войти.
- Access JWT содержит идентификатор пользователя, роль, одну систему, список регионов зоны, срок действия, issuer и audience. Проверяется подпись HS256 и обязательные claims. Чтение данных не требует обращения к таблицам пользователей.
- Access-токен действует 300 секунд (AUTH_ACCESS_TTL_S, допустимо 30–900). Refresh-токен — случайная непрозрачная строка; в app.auth_session хранится только SHA-256-хеш. Срок refresh — 7 дней (AUTH_REFRESH_TTL_S, 300–2592000 секунд).
- POST /api/v1/auth/refresh принимает {"refresh_token": "..."}, перечитывает актуальные права и атомарно заменяет refresh-токен. Повторное использование старого, в том числе параллельное, возвращает 401. Система сеанса сохраняется; для другой системы нужен новый вход.
- POST /api/v1/auth/logout с тем же телом отзывает refresh-токен и возвращает 204. Клиент удаляет оба токена.
- GET /api/v1/auth/me возвращает ID, роль, систему, регионы и срок действия текущего access-токена.
- Смена пароля, роли, активности, назначения зоны или состава зоны отзывает refresh-сеансы затронутых пользователей. **Уже выданные access-токены продолжают действовать до exp, по умолчанию не более пяти минут**, включая административные права. Это граница отзыва при локальной проверке JWT, принятой в ADR-0002. После изменения прав нужен повторный вход.
- Вход ограничен десятью попытками за минуту с одного IP на процесс; одновременно выполняются не более четырёх проверок пароля. Ответ 429 содержит Retry-After: 60; таблица ограничителя ограничена 4096 IP. Заголовки X-Forwarded-For приложение самостоятельно не использует; доверенные proxy настраиваются при развёртывании.
- Ответы API запрещают HTTP-кэширование (Cache-Control: no-store). Токены передаются заголовком, а не в URL. Внешний доступ должен идти через HTTPS.

## Права

**Оператор** видит справочники, текущее состояние, события и агрегаты своей зоны; запрашивает историю интервалами до суток для карточки станции. Данные чужой системы запрещены.

**Менеджер** видит справочники и ролл-апы своей зоны. GET /api/v1/systems/{system_id}/catalog возвращает доступные станции без текущего состояния (items, next_after; параметры limit и after), чтобы выбрать станцию для отчёта. Текущие состояния, сырая история, события и SSE возвращают 403. У PostgreSQL-роли app_manager нет SELECT на core.station_current, core.station_status и их партиции.

**Администратор** читает все системы и управляет пользователями, зонами, назначениями и журналом действий. Самому себе нельзя снять административную роль или отключить учётную запись.

Список систем ограничен системой access-токена. При отсутствии назначения вход возвращает 403 scope_required. Пустая зона даёт 403 scope_empty; запрос чужой системы — 403 system_forbidden. Станция вне доступной зоны неотличима от неизвестной: 404 station_not_found. Нет токена, неверная подпись или истёкший токен — 401 с WWW-Authenticate: Bearer.

## Зоны и администрирование

Зона принадлежит одной системе и содержит region_ids из её GBFS-справочника:

- null означает всю систему, включая станции без region_id;
- список регионов ограничивает выборку их станциями;
- [] означает отсутствие доступных станций, а не всю систему.

Зона «Вся система» создаётся миграцией для известных систем, а для новых — при первом административном чтении списка зон. Её название и состав зарезервированы. Создание зоны само по себе никому не выдаёт доступ. app.user_scope связывает пользователя, систему и одну зону; составной внешний ключ исключает назначение зоны другой системы.

Административные маршруты (префикс /api/v1/admin):

- GET /systems, GET /systems/{system_id}/regions — справочники для выбора системы и состава зоны.
- GET /users, POST /users — список и создание пользователя (username, password, role: operator, manager, admin).
- PATCH /users/{id} — изменение role, active и/или password. Хеши паролей API не возвращает.
- GET /zones?system_id=..., POST /zones — список и создание зоны (system_id, name, region_ids).
- PUT /zones/{id} — замена названия и состава зоны в той же системе; DELETE /zones/{id} — удаление неназначенной зоны. Занятая зона возвращает 409.
- GET /users/{id}/scopes, PUT /users/{id}/scopes/{system_id} с {"zone_id": 123}, DELETE /users/{id}/scopes/{system_id} — назначения.
- GET /audit?before=...&limit=100 — журнал действий, от новых к старым. У списков пользователей, зон и справочников курсор after, максимум 500 строк на запрос.

Порядок настройки оператора: дождаться загрузки справочников, выбрать систему, создать зону или взять «Вся система», создать пользователя и назначить ему зону. Войти его логином с выбранным system_id.

В app.audit_log сохраняются входы, выходы и изменения учётных записей, зон и назначений. Пароли, хеши паролей и токены в журнал не попадают. У ролей API нет прав изменения и удаления строк аудита.

## Изоляция данных

Для каждого запроса чтения приложение устанавливает SET LOCAL ROLE и транзакционные параметры app.system_id / app.regions. Роли app_operator и app_manager используют RLS; отсутствующий контекст закрывает доступ. Настройки не переносятся на следующий запрос при возврате соединения в пул. app_api переключает роли, но не наследует их права и не имеет прямого чтения core/mart.

Зона станции определяется её действующей SCD2-версией. Оператор и менеджер получают факты и агрегаты только станций, действующих в доступной зоне сейчас. Исторические версии и данные закрытых станций сохраняются и доступны администратору. Перенос станции между регионами меняет её доступность при следующем чтении, с учётом TTL кэша.

Сервисные роли app_ingest / app_analytics продолжают читать и записывать свои данные. R загружает ролл-апы через COPY во временную таблицу со схемой LIKE mart.station_rollup, затем выполняет INSERT в защищённую таблицу: прямой COPY несовместим с RLS. RLS на родительской таблице фактов действует при чтении партиций через неё; прямые гранты на партиции пользователям не выдаются.

Ключи внутреннего TTL-кэша, объединения запросов, начальных SSE-снимков и групп подписчиков включают роль, систему и регионы. Пользователи одной области могут совместно использовать результат; разные области не смешиваются. При уходе станции из зоны SSE передаёт её ID в removed, не передавая новое состояние. По истечении access-токена поток выдаёт auth_expired и закрывается; клиент обновляет токен и подключается с новым снимком. Для браузера используется потоковый fetch с заголовком авторизации.

## Проверка

Из services/api команда uv run pytest проверяет миграцию, её откат и alembic check, прежние сценарии M1/M2 и M3:

- вход, ошибочные claims/подписи и сроки действия, хеширование, ротацию и конкурентное обновление refresh;
- смену ролей и паролей, блокировку, назначения, аудит и ограничения административных операций;
- запрет чтения чужих зон и систем, защиту прогретого кэша, права менеджера и сброс контекста соединения;
- фильтрацию SSE-снимков, дельт и удалений, истечение токена и освобождение подписок.

Нагрузочным сценариям теперь нужен BENCH_TOKEN; прежние результаты M2 не являются замером M3. См. [benchmarks/README.md](../benchmarks/README.md).

Реализация следует [ADR-0002](adr/0002-arhitektura-m0.md). Правила проверки JWT — [PyJWT](https://pyjwt.readthedocs.io/en/stable/usage.html), поведение политик — [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).
